# Agentic workflow alignment with current research

Assessed on 2026-11-07. **The workflow is well aligned with current verification and context-management practices. Its orchestration efficiency and reliability remain unproven by comparative evaluation.** The most useful next step is to measure which roles and gates improve outcomes before expanding the workflow.

The reviewed package describes itself as portable instructions, templates and local helpers; an automated runner is explicitly outside its distribution. That is a deliberate scope boundary, not a missing implementation of a promised feature. This assessment covers the package's entry points, roles, policies, templates, helper checks and evaluation design. It does not infer performance from earlier task histories. The base commit was `3cb36cc`; separate eval-tooling edits occurred during the assessment.

## Gaps that matter most

**1. The evaluation cannot establish a performance advantage.** The [todolist evaluator](../evals/todolist.py) exercises eleven CLI commands in one application scenario. Its artifact grade deliberately allows empty trace/report files. The [eval guide](../evals/README.md#todolist-end-to-end-eval) excludes content auditing, repeated-trial statistics and baseline comparisons. This is useful smoke coverage, but it cannot show that the Supervisor, per-task review, model routes or memory improve completion rates. Current [evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) supports repeated trials, observable outcomes and complementary graders. Improving this evidence is the highest-priority change.

**2. Full-mode coordination has no measured payoff here.** The [Supervisor](../agentic-workflow/roles/SUPERVISOR.md) dispatches tasks and manages writer pauses; the [Implementer](../agentic-workflow/roles/IMPLEMENTER.md#review-a-full-mode-task) launches a fresh reviewer for each full-mode review cycle; a final validator follows. Each boundary can catch failures, but also adds communication and context rebuilding. Recent [deployment guidance](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) supports selective consolidation. The [September harness study](https://arxiv.org/abs/2609.32459) also finds task-dependent benefits, including gains from specific verification subagents. Neither establishes that this package should remove every task reviewer or replace its Supervisor unconditionally.

**3. Execution guarantees depend on the host.** The package has real record-allocation and trace locks, but task scheduling, acceptance transitions and writer pauses remain agent instructions. [Runner](../agentic-workflow/guides/RUNNER.md) is explicitly future work. [Model routing](../agentic-workflow/policies/MODELS.md#route-selection) escalates repeated failures, but does not impose a repair-attempt or spend ceiling; the eval separately enforces a wall-clock timeout. If unattended operation becomes a goal, enforce budgets and transitions in the host or a small runner, and test interrupted recovery and repeated side effects. A hosted orchestration platform is not a prerequisite.

**4. Instruction and review costs need measurement.** Shared policies are sensibly centralized, but every new role reloads part of the same guidance. The [AGENTS.md study](https://arxiv.org/html/2602.11988v3) gives reason to test the value of extra context, not to discard repository constraints. Likewise, measure reviewer false positives and missed defects using known faulty candidates and human adjudication. Requirements-first review is a good procedure; its effectiveness remains a separate question.

## Recommended comparison

- Context: evaluate architecture changes before revising the package's execution contract.
- Inputs: use the same specifications, acceptance graders, model versions, environments and total budget ceilings across variants. Include bounded changes, interacting components, debugging, persistence failures and interrupted work.
- Effects: compare the current workflow with one builder plus an independent final validator, then add selected task reviews to that simpler baseline. Repeat each task and retain individual outcomes. Evaluate a deterministic dispatcher separately if coordination dominates the measured overhead.
- Outputs: compare verified completion, escaped defects, reviewer errors, repair rounds, elapsed time, token use or measured cost, and human intervention. Validate report contents separately from application behavior; keep unknown telemetry unavailable.
- Next: retain the simplest variant that meets the required quality and reliability. Recheck the decision after model or tool changes. These are proposed experiments, not findings that the simpler variants already win.

## Primary source findings

Publication dates and paper revisions are explicit below. The sources do not establish one universally best workflow; the local recommendations above are engineering judgments, not measurements of this repository's performance.

1. **Selective orchestration — 2026-10-22, first-party deployment report.** Anthropic reports that consolidating planners, routers, and domain specialists into one loop with progressively loaded skills often improved quality, cost, and latency. It retains subagents for independent verification, parallel tasks, permission boundaries, and demonstrated context or tool-selection problems. It recommends changing one boundary at a time and checking individual task regressions over repeated runs. **Limit:** enterprise examples lack a public controlled dataset; the reported roughly twofold runtime improvement is one customer's observation. **Implication:** compare simple and elaborate workflows locally; role count is not evidence of quality. [Building agents](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

2. **Architecture depends on task structure — revised 2026-04-08, controlled preprint, v3; first submitted 2025-12-09.** Across 260 configurations, six benchmarks, and five architectures, relative changes versus a single agent range from +80.8% on decomposable financial reasoning to −70% on sequential planning. Coordination helps selectively and incurs substantial overhead. **Limits:** software evidence uses only 20 SWE-bench Verified and 20 Terminal-Bench instances; cross-validated explanatory power is modest, and task-specific optimal thresholds should not be generalized. **Implication:** test delegation on separable work, with matched budgets and an explicit single-agent baseline. [Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v3)

3. **Measure components, not architectural labels — 2026-09-26, controlled preprint.** Ten models and two harnesses are compared across three task families; component ablations use 200 ProgramBench tasks and two models. Structured tools and task-specific behavior-analysis/testing/review subagents help most consistently; generic software-role subagents and the tested compression scheme hurt in isolation. Combined components improve scores by 7.37 and 6.21 percentage points. **Limits:** only two model families, non-thinking configurations, and benchmark-specific implementations; these are score gains, not whole-project success rates. **Implication:** evaluate each gate, role, and context mechanism against the failures it is intended to prevent. [Beyond the Model](https://arxiv.org/html/2609.32459v1)

4. **Independent evaluation needs calibration — 2026-03-24, first-party engineering experiment.** A planner–generator–evaluator harness checks live UI, API, and database behavior against explicit criteria. Evaluator prompts required repeated tuning against human judgment. A showcased full harness cost $200 over six hours versus $9 over twenty minutes solo, while also expanding scope. Later iterations removed sprint boundaries and reduced evaluation frequency where capability made them unnecessary. **Limit:** demonstrations vary scope, compute, and model; they do not isolate a universal multi-agent benefit. **Implication:** retain independent verification where it catches material failures, and measure its incremental value. [Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps)

5. **Instruction files impose measurable costs — revised 2026-09-29, controlled preprint, v3; first submitted 2026-02-12.** On 300 SWE-bench Lite tasks and 138 CTXbench tasks, generated context files do not significantly improve resolution and increase mean inference cost by 20% and 23%, respectively. Developer files improve resolution by 2.4 points on average, but not significantly versus no file (p=0.21). **Limits:** Python repositories, one completion per agent/task/condition, and test-based resolution rather than security or maintainability. This does not evaluate all forms of persistent memory. **Implication:** preserve necessary repository constraints, and test whether extra navigation or process instructions earn their cost. [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988v3)

6. **Audit the grader itself — 2026-07-08, first-party benchmark audit.** OpenAI estimates roughly 30% of SWE-Bench Pro's 731 public tasks are broken: strict implementation assumptions, missing requirements, inadequate coverage, or misleading prompts. Five engineers independently reviewed each flagged task; agent and human reviews identified 200 and 249 broken tasks respectively. **Limit:** deeper review targeted 286 automatically flagged tasks, rather than a random sample of every task. **Implication:** a passing grader needs its own evidence of validity; audit both false failures and incomplete solutions that pass. [Separating signal from noise](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)

7. **Evaluate outcomes and repeatability — 2026-01-09, first-party engineering guidance.** Anthropic distinguishes final environment state from an agent's completion claim, recommends multiple trials, combines deterministic checks with calibrated judgments, and separates capability from regression suites. It distinguishes success at least once across attempts from success on every attempt. **Limit:** practice guidance, not a controlled estimate of workflow improvement. **Implication:** record verified completion, repeated-run reliability, tokens/cost, elapsed time, and human repair; retain traces to explain failures rather than treating logs as proof of success. [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

8. **Durability is an execution property — undated documentation, accessed 2026-11-07.** LangGraph documents bounded retries, attempt timeouts, checkpoint boundaries, and recovery handlers. Retrying a node re-executes it; checkpoints do not make external side effects happen exactly once. Applications need durable operation identity and idempotent effects where repetition matters. **Limit:** runtime behavior documentation, not evidence that adopting this framework improves coding quality. **Implication:** assess crash recovery and retry bounds when unattended execution is in scope; written handoffs alone cannot establish those guarantees. [Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)
