# Evidence on agentic software-development orchestration

Research date: 2026-11-06. Sources below were retrieved on that date. Publication and paper-version dates are recorded separately; relative search-result timestamps were not treated as publication dates. Scope: primary research and first-party engineering experience relevant to a deterministic task-agent loop, independent evaluation, and an LLM supervisor. This note does not inspect local suite history or claim to benchmark the suite.

The defensible conclusion is conditional: deterministic scheduling around capable task agents is a sound candidate when tasks and dependency rules are already specified. Current evidence does not establish a permanent LLM supervisor, a fixed number of agent roles, or per-task independent review as universally optimal. It also does not establish that a single final browser check is sufficient. Keep verification quality distinct from the choice of scheduler.

## Implications for a proposed deterministic task loop

The following are engineering inferences, not findings from an experiment on this repository:

1. **Separate deciding the work from dispatching it.** Once a task graph, prerequisite policy, and acceptance rules exist, a program can select ready tasks, launch isolated sessions, validate result schemas, persist state, and enforce retry limits. Invoke reasoning for unresolved requirements, new dependencies, contradictory evidence, or recovery choices. Sources 1, 3, and 5 support this separation without proving its exact performance.
2. **Do not confuse fewer reviewers with weaker verification.** A final evaluator can cover assembled behavior and inspect implementation evidence. Deterministic type, build, regression, and contract checks can run during task execution without another agent role. Review code-level or cross-task concerns where a browser journey cannot establish the requirement. Sources 4, 6, 7, and 9 motivate complementary evidence; none establishes that every task needs another LLM reviewer.
3. **Treat evaluation as a bounded repair loop.** A failed integration check should produce reproducible findings and route a repair before reevaluation. A final agent that merely reports success is not an acceptance mechanism. Preserve an explicit unresolved/blocked outcome when the budget is exhausted.
4. **Ablate overhead instead of assuming it is valuable.** Compare the current arrangement with deterministic dispatch plus final evaluation, and with selective review for higher-dependency tasks. Keep task inputs, model settings, budgets, and environment comparable; repeat runs and inspect which tasks change outcome. Measure accepted functionality, regressions, tokens/cost, wall-clock time, rework, and human intervention. Sources 6 and 10 support this evaluation approach.

## Confidence and limits

There is no demonstrated universal “state-of-the-art architecture” in these sources. The academic studies cover bounded tasks and particular model generations; the application-building reports are informative but selective first-party experience. None is a controlled comparison of this repository's suite against the proposed launcher. Observational quality improvements can confound model upgrades, token budgets, tool changes, prompts, and task difficulty.

Independent context reduces direct dependence on the implementer's narrative; it does not make two instances of the same model statistically independent or guarantee a correct verdict. E2E testing observes exercised paths, while static checks and review answer different questions. The right amount and timing of review should therefore remain an empirical decision tied to requirements and observed failure modes.

The strongest recommendation is to preserve clear specifications, durable handoffs, executable checks, and assembled-app validation while measuring whether supervisory turns and mandatory per-task reviews earn their cost. This is an assessment direction, not authorization to change the suite's current contract gates.
