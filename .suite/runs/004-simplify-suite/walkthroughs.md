# Documentation walkthroughs

Method: manually follow the final entry points and templates for the scenarios below. These are instruction walkthroughs, not executed app workflows, worker-adapter tests or isolation experiments.

| Scenario | Route and expected disposition | Assessment |
|---|---|---|
| Document authoring | Root router → Define steps 1–4 → bundle/plan/acceptance templates. Save full documents, map source clauses and validate consistency, references, graph and verification descriptions. Document scope ends there; no app runtime/reviewer is required. Define step 5 records results, useful memory and usage. | PASS: clear document completion distinct from generation readiness; local acceptance skill recognizes existing implementation authorization. |
| Implementation with repairs | Implement reads complete records → builds/tests → fresh Reviewer with requirements, acceptance, candidate, results and prior findings. Exclude plan/conversation/memory from the handoff, including forwarded reports. Reviewer inspects and executes independently. Finding returns to retained implementer; changed candidate reruns affected checks/regressions and receives another fresh reviewer until none remain. | PASS: no frozen expectations, manifests, receipts or exhaustive attempt inventory; requirement violations cannot be waived by changing expectations. |
| Dependent tasks carrying memory | Generate validates ordered/explicit prerequisites; plans only ready task A with Define. Ordinary planner reads selected project's memory index/relevant notes. A must be accepted before B is planned; B receives relevant note paths and accepted interfaces. Completing agents save useful supported lessons, including at blocked stops. | PASS: live index/notes retained; no metadata schema, copies or hashes. |
| Unavailable independent review | Implement cannot spawn a fresh context. Shared rule 5 and Reviewer return INDEPENDENT_REVIEW_NOT_RUN. Generate acceptance step does not unlock consumers; concise results retain blockers and available usage. | PASS: self-review cannot stand in for required independent review. |
| Unavailable checks or conflicting requirements | Shared rules 1, 3–4: resolve ordinary details autonomously; record substitutes and coverage limits. Missing required service/manual check blocks acceptance, skipped execution is NOT_RUN/BLOCKED. Conflicting required behavior needs a decision. Reviewer independently assesses whether remaining evidence supports acceptance. | PASS: no routine approval loop and no unavailable check reported as PASS. |
| Assembled-app failure | Tasks A/B pass; Generate step 6 runs final scenarios on the actual assembled candidate. Cross-task failure leaves the app incomplete, returns to the retained implementer, triggers affected checks/review and renewed final scenarios. Changed accepted work prompts downstream reassessment. | PASS: task successes alone cannot establish app completion. |
| Reconstruction exclusions | Generate branches to Regeneration before planning/dispatch. New workspace and fresh workers receive approved requirements/acceptance/contracts/assets; exclude old implementation, builds, history, conversations, old plans and all memory/copies. New plans come only from allowed inputs. Preserve behavior across targets; test required retained boundaries. Declare procedural limits; unavailable required enforcement blocks the claim. Known leakage invalidates reconstruction claims. | PASS: prior implementation preserved, no metadata/hash validation gate; procedural isolation is not represented as enforcement. |
| Missing telemetry and blocked runs | Generate captures supervisor/implementer/reviewer session/turn references as they run. Helpers guide aggregation with the unchanged version 1 schema. Results link source references plus totals/per-role/session reports. Missing logs/counters are explicit; partial reports identify included scope and known subtotals. Telemetry availability does not affect app acceptance. | PASS: blocked execution still records available usage; source selection adds no approval or integrity gate. |

Additional inspection: shared rules and each entry point/template contain no positive requirement for the removed mechanisms. The remaining mentions explicitly state their removal or describe package distribution metadata. The future runner assignment/acceptance uses the same simplified workflow. Historical research describes its original snapshot and is marked accordingly.
