+# Acceptance specification
+
+Use the planning discussion as the source of agreed scope. Read relevant repository
+contracts when needed to make criteria precise. Extract agreed requirements,
+contracts, edge cases, failure scenarios, non-goals, and verification criteria;
+resolve material ambiguities with the user rather than inventing requirements.
+Keep implementation choices open unless the user explicitly requires them.
+
+Choose a short task ID suitable for a directory name, reusing the user's ID when
+provided. Record the full baseline Git commit before implementation, normally
+`git rev-parse HEAD`; if work has already started, establish the actual baseline
+with the user. Present a concise draft containing the task ID, baseline commit,
+goal, scope and non-goals, and numbered acceptance criteria. Give each criterion
+a stable ID such as AC-1, one independently verifiable outcome, and a concrete
+verification method with the relevant inputs, conditions, and expected result.
+Include agreed boundary and failure behavior in the criteria. Keep unresolved
+questions visibly separate from agreed requirements.
+
+Present the complete draft in the conversation and explicitly ask the user to
+approve it. Wait for explicit approval of the current draft; revisions require
+presenting the revised draft for approval. Save only after approval, using
+`.agents/tasks/<task-id>/acceptance.md`, and preserve the approved text exactly.
+Do not overwrite an existing approved specification without explicit authorization.
+When the task uses this repository's specification workflow, also preserve the
+complete approved plan as `plan.md` in the same directory and record both document
+digests, the full baseline commit, approving authority, and approval reference.
+Follow [the shared contract](../../../spec-source-suite/docs/SUITE_CONTRACT.md)
+§2 for task persistence. Register a subsystem's acceptance.md directly as its
+specification; do not duplicate it in a second requirements document.
+
+If Plan mode prevents writing, present the complete drafts and state that saving
+is deferred. Save the exact approved text once editing is available, before
+implementation or context handoff. Recover missing originals instead of rebuilding
+them from a summary. Report the saved paths. Approval alone never starts
+implementation; a separate instruction is required. If that instruction already
+exists, continue within its authorized scope rather than asking again.
+
+Treat the approved document as immutable. If later discoveries require a change,
+present the proposed revision and obtain explicit authorization before editing;
+never weaken or silently reinterpret criteria to fit an implementation.

+# App generation
+
+This repository uses `spec-source-suite/` as reusable guidance for generating an app. The app's specification bundle lives outside that directory and defines what to build. Keep app specifications, target profiles, retained assets, generated code, and run evidence outside the suite. Modify the suite itself only when the user requests changes to the workflow tooling or guidance.
+
+## Load the workflow
+
+Before defining, implementing, or generating an app, read [the suite instructions](spec-source-suite/AGENTS.md) and [the shared contract](spec-source-suite/docs/SUITE_CONTRACT.md). Their workflow boundaries and acceptance gates apply to app work throughout this repository. Resolve relative paths in suite documents from the containing document, not from this project root.
+
+Select the procedure that matches the requested work and read both its skill file and workflow document directly; the nested skills need not be installed or automatically discovered:
+
+| Requested work | Skill instructions | Workflow |
+|---|---|---|
+| Define or revise app behavior and acceptance criteria | [spec-define](spec-source-suite/.agents/skills/spec-define/SKILL.md) | [Define](spec-source-suite/docs/DEFINE.md) |
+| Implement an approved capability or assess alignment | [spec-implement](spec-source-suite/.agents/skills/spec-implement/SKILL.md) | [Implement](spec-source-suite/docs/IMPLEMENT.md) |
+| Generate an app, update it incrementally, regenerate it, or change its target technology | [spec-generate](spec-source-suite/.agents/skills/spec-generate/SKILL.md) | [Generate](spec-source-suite/docs/GENERATE.md) |
+
+For generation, also read the Implement skill and workflow: Generate orchestrates that procedure for each selected capability. Read `spec-source-suite/CODEX_START.md` and `spec-source-suite/docs/BUILD_THE_SUITE.md` only when explicitly asked to build the suite's tooling; they are not the app specification.
+
+## Locate the app inputs
+
+1. Use the specification location or project manifest identified by the user. Otherwise inspect the repository outside `spec-source-suite/` for the intended app brief, specifications, and manifest. If multiple bundles are plausible, ask which one is authoritative before implementing.
+2. Read the app brief and all specs selected for the requested scope, including their prerequisite specs and normative references. Follow the manifest's registered paths; manifest paths are relative to its directory unless it explicitly declares a controlled external verifier reference.
+3. If the user supplies a brief or draft specs, follow Define to prepare the missing acceptance criteria and manifest before generation. When creating a new bundle without an established location, use `specs/` at the project root. Copy only the needed [templates](spec-source-suite/templates/) there and fill them from the user's requirements. Preserve an existing bundle's location and structure.
+4. Treat suite templates as blank scaffolding and `BUILD_THE_SUITE.md` as a tooling specification. Neither supplies app requirements. Register each subsystem’s authoritative `.agents/tasks/<task-id>/acceptance.md` directly as its spec; keep the approved `plan.md`, baseline commit, and digest-bound approval references alongside it. Historical task notes are not automatically selected specifications. If no app specifications are available, report `NO_PROJECT` and identify the missing input; use Define if the user has requested specification authoring.
+
+## Execute and finish
+
+Before implementation, establish the approved specification baseline, selected requirement IDs and scope, dependency graph, target profile, verification arrangement, retained inputs, and authorized output paths required by the shared contract. Use existing approvals and delegated choices where applicable. Resolve missing decisions with the user instead of inventing a domain, stack, or deployment model. Missing required execution inputs yield `BLOCKED`.
+
+Follow Generate's mode-specific workspace rules and Implement's review and verification loop. Keep the app bundle and acceptance baseline protected from implementation changes. Persist run state and requirement-linked evidence in the app manifest's configured evidence directory, outside `spec-source-suite/`. Use the suite’s concise run-report and review templates when those steps are reached; a separate verification-design document is optional when acceptance contains the mapping. Follow the shared contract for planner-authored frozen checks, the implementer-spawned fresh reviewer, and the bounded correction loop. Initial and incremental work use procedural separation unless stronger isolation is explicitly required.
+
+Completion requires every mandatory gate for the selected scope to pass, including independent review, applicable manual acceptance, and assembled-app checks for project acceptance. Report actual checks, unmet requirements, evidence paths, and any isolation or execution limitations. When a required capability is unavailable, preserve partial evidence and report the blocked gate rather than claiming success.
