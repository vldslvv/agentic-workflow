# Independent procedural observations

Reviewer: /root/independent_review. Method: manually trace concrete hypothetical states through the final documents. These observations are documentation acceptance, not execution of a scheduler or app. No fixtures, app, or runtime were created.

1. Ordinary route: root AGENTS → suite AGENTS → shared contract; Define skill/D1–D4 prepares authoritative task acceptance, plan, approval record, target and check inventory. Generate G1–G2 resolves initial output ownership and readiness. G3 dispatches Implement I1–I5; I3 spawns a fresh reviewer and G4 checks assembly. The contract is the shared rule authority. No requirement to load regeneration or enforced isolation for this route.
2. Persistence → CLI: registered PERSISTENCE has no prerequisites, CLI has depends_on=[PERSISTENCE]. With no accepted outputs only PERSISTENCE is ready (§5). Local test success alone cannot unlock CLI (§7). Supervisor acceptance against the required identity unlocks CLI; CLI must subsequently pass real integration, review and all selected checks. Project acceptance still awaits G4.
3. Failed persistence: PERSISTENCE FAIL leaves CLI BLOCKED, including when CLI is selected with only/start-after/skip (§5). A stub or unreviewed candidate cannot substitute for acceptance. Remaining repair allowance belongs to the failed task (§6).
4. Unknown dependency: CLI depends_on=[MISSING] where MISSING is unregistered. Graph validation fails before dispatch (§5, G2); prescribed status BLOCKED, no invented dependency.
5. Cycle: PERSISTENCE depends_on=[CLI] and CLI depends_on=[PERSISTENCE]. Validation blocks dispatch (§5); resolution requires approved boundary changes and cannot delete an edge merely to dispatch.
6. Successful repair: attempt 0 has a confirmed implementation mismatch. Preserve identity, failed assertion and review. Attempt 1 corrects implementation within owned paths; I4 returns to I2/I3, requiring checks and fresh review. Only the new identity can pass. Attempt 0 remains FAIL in the report (§6).
7. Exhaustion: attempts 0, 1 and 2 each fail the same mandatory requirement. Stop FAIL with partial evidence; no automatic attempt 3 or session reset. Additional work requires recorded explicit authorization (§6).
8. Conflicting requirements: freeze contains two incompatible assertions. Do not choose an interpretation or repair assertions. Immediately hold affected work SPEC_CONFLICT/BLOCKED, escalate through supervisor to Define, obtain authorized versioned resolution, refreeze and invalidate affected evidence (§§2,4,6).
9. Defective verifier: an assertion contradicts its named requirement. Preserve failure and escalate before further evaluation. Implementer cannot change the frozen assertion. Corrected baseline requires authorization and freezing; earlier failed attempts survive (§6, CHANGE template).
10. Missing runtime or fresh reviewer: missing required tool/service is INFRA_ERROR/BLOCKED and does not spend behavioral repair rounds. Missing fresh context is INDEPENDENT_REVIEW_NOT_RUN and blocks acceptance. Unassessed requirements remain NOT_RUN (§§3,6,7).
11. Integrity violation: a worker edits frozen fixtures. Before/after inventory comparison detects it; §4 invalidates the attempt, preserves the incident and requires supervisor restoration/resolution. A matching digest is explicitly described as detection rather than an enforced sandbox.
12. Downstream invalidation: an approved persistence revision changes an input used by accepted CLI. §7 invalidates affected downstream and assembly evidence; old completion does not unlock work on resume. Relevant identities and evidence must be rechecked.
13. Assembly failure: PERSISTENCE and CLI pass separately but an interaction fails after combining. G4 and §7 prohibit project PASS, route failure through §6 and require affected checks again. There is no separate unlimited assembly retry loop.
14. Plan-mode persistence: full plan and acceptance drafts are approved while writes unavailable. §2 requires explicit deferral, then exact saving with baseline/digests/approval before implementation or handoff. Missing originals must be recovered, not reconstructed from summaries. Later revisions require authorized versioning. Separate implementation instruction is still required, including preservation of existing authorization across handoffs.
15. Independent handoff: planner supplies complete documents to implementer. Implementer sends reviewer acceptance, normative inputs, identities, selected IDs, candidate and checks/results, but excludes plan and conversation. §3 requires fork_turns="none" or equivalent; REVIEWER requires independent coverage assessment and execution, before/after integrity, and reviewer-owned outputs.
16. Enforced branch: a requested enforcement boundary without available controls yields BLOCKED. STRONG_ISOLATION requires testing permitted writes and rejected access; a directory or fresh context alone cannot support an enforced claim.
17. Regeneration branch: REGENERATION requires explicit allowlisted export into a new workspace, excludes prior scoped source/history/old plans/transcripts/build caches, checks path escape and final export hashes, preserves verifier behavior, identifies retained boundaries, tests real dependency integration, and invalidates reconstruction claims on leakage. Procedural regeneration requires explicit policy and a weaker claim. Source deletion and unsupported equivalence/reliability claims are prohibited.

All observations above match the prescribed outcomes. No application execution or enforced separation was demonstrated.
