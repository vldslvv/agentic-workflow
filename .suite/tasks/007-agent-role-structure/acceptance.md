## Requirement sources

These source clauses record the agreed requirements from the current discussion and final design, without implementation plans, private planning rationale, or project memory. They are the source references for the acceptance table and can be supplied to an independent reviewer.

### S1 Purpose and layout

The user requested simplification by “merging the documents that have no purpose being separated.” Q1 selected shared rules plus role files; Q8 selected flat instruction files. Q16 confirmed six core files: `AGENTS.md`, `SUPERVISOR.md`, `PLANNER.md`, `IMPLEMENTER.md`, `REVIEWER.md`, and `VALIDATOR.md`. Each agent reads shared instructions plus its own routine. The final design removes the superseded README, supporting guides, `docs/`, and `prompts/`, consolidating their necessary content.

### S2 Supervisor and planner

The user specified: “Supervisor should not plan, but only orchestrate” and “Task planner is isolated within each task implementation.” Q5 selected task planners integrating current project constraints and accepted dependency state, without a separate project-wide planning stage. Q7 retained each task planner for corrections. The supervisor retains scheduling/status/path/agent-reference context; each fresh task planner receives relevant specifications, current code, dependency contracts, and memory, and produces full plan and acceptance records.

### S3 Implementation and independent review

Q4 selected original specifications plus acceptance for reviewers. Q6 assigned the fresh-review repair loop to the implementer. The confirmed design gives implementers task specifications, plan, acceptance, relevant state, memory, and access to their task planner. Reviewers independently inspect and execute checks against requirements, acceptance, code, results, contracts, and prior findings; plans, conversations, and memory are excluded. The implementer remains through repairs; each review uses a fresh context.

### S4 Final validation and repair tasks

Q3 selected one fresh final validator. The user specified a “separate repair task that follows the regular routine with the only difference that specification will be generated by validator dynamically.” Q13 limited repairs to existing requirements; Q14 selected extending the app bundle; Q15 selected one repair task per failed validation pass. Q16 confirmed that the validator authors a repair specification and appends it to the task order. The final design names these `tasks/repair-NNN.md`, uses the next unused number, resumes existing recorded repairs, and requires a new planner/implementer plus regular review before another fresh final validation. The validator reads project requirements, all task acceptances, assembled code, check results, and prior validation findings, excluding plans, conversations, and memory.

### S5 Templates and entry points

Q9 retained only the four app-bundle template types; the user noted that further template reduction “is not the focus at the moment.” Q10 selected renaming skills around roles. Q16 confirmed `spec-planner` and `spec-supervisor`, retirement of the three old names, and keeping bundle templates directly under `templates/`. The final design places plan/acceptance outlines in planner instructions and the common result outline in shared instructions. Document-only work ends with validated documents; single-task and whole-app execution enter through the supervisor.

### S6 Optional runner and retained behavior

Q11 selected one optional future-runner document, excluded from ordinary startup; Q16 confirmed `RUNNER.md`. The final design preserves existing task/run locations, complete approved records, history, memory storage, reconstruction exclusions, and requirement-linked results. Tasks remain serial and prerequisite-gated by default. Changes to required behavior need user authority. Required unavailable capabilities and unresolved requirements remain blockers. Reconstruction uses fresh allowed-input contexts and reports actual isolation limits.

### S7 Usage and validation

The final design preserves the usage helper implementation, CLI, output schema, and tests. Capture usage references for all five roles, repair work, and blocked work; missing telemetry never blocks acceptance. Validate links, skills, inventories, role loading, retained tests, and scenario walkthroughs. Report before/after instruction words, files, and directories without imposing a numeric reduction target. Distinguish actual checks and documentation walkthroughs from live app generation.

### S8 Change boundaries

The final design leaves existing app bundles and historical records untouched during this refactor. Only future execution of the repair workflow extends a selected bundle. Preserve unrelated app changes. The latest request is solely to save the plan and acceptance document.
