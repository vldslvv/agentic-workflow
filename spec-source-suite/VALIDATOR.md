# Validator

Read [AGENTS.md](AGENTS.md) plus this routine in a fresh context after all scheduled tasks pass. Inputs: project/task requirements, task modes, full-task acceptances, lightweight source criteria, assembled implementation, check commands/results, contracts and prior validation findings. Exclude plans, conversations, memory and design narratives, including copies.

1. Establish expected behavior from original requirements and engineering guidelines before reading acceptance or code. Check full-task acceptance for source fidelity; lightweight tasks use source criteria directly and need no acceptance document or task-review result. Independently inspect whole-app behavior, task interactions and coverage, including the reasons for material guideline exceptions. Run final scenarios on the actual assembled app, required real-dependency integration and applicable manual checks; add feasible reproductions for suspected gaps. Record requirement-linked methods, outcomes and coverage limits using the common result outline. Keep the candidate unchanged during validation; changes require a fresh pass.
2. PASS requires successful required checks, sufficient coverage and zero actionable failures, regardless of task mode. Missing capabilities or unresolved requirements remain blockers, not repair tasks. Return planning/acceptance defects with source task references to the implementer; behavior changes require user authority.
3. For implementation failures grounded in existing requirements, create one `tasks/repair-NNN.md` in the selected bundle per failed validation pass, covering all actionable findings. Use the next unused number across repair files and table rows. Each finding includes its source requirement, expected/observed behavior and reproduction evidence; include scope and required rechecks. Add one `task_order.md` row depending on every validated task (including earlier repairs) and any other required prerequisites. Preserve existing specifications and rows; do not edit implementation.
4. Before writing the repair, save the pass/result, intended path and full dependency list in run evidence. On resume, inspect that record, file and table row; reuse the reserved path and complete only missing or incomplete content, preserving findings and dependencies. If older evidence lacks dependencies, recover them from that pass's validation scope; missing or ambiguous scope blocks completion. Conflicting rows or paths owned by another pass also block completion. Never overwrite conflicts or duplicate a pass's repair. A later failed validation after repair acceptance may receive the next number.
5. Return status, result path under `runs/validation/<agent-run-id>/`, repair specification/order references, blockers and usage references. The supervisor schedules repairs and fresh validation; the validator never implements its repairs.
