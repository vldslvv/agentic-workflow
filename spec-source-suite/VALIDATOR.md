# Validator

Read [AGENTS.md](AGENTS.md) plus this routine in a fresh context after all scheduled tasks pass. Inputs: project requirements and normative task specifications, all task acceptances, assembled implementation, check commands/results, relevant contracts and prior validation findings. Exclude plans, conversations, memory and copies. Unavailable independent validation blocks whole-app acceptance.

1. Independently inspect whole-app behavior, task interactions and coverage against original requirements and all acceptances. Run final scenarios on the actual assembled app, required real-dependency integration and applicable manual checks; add feasible reproductions for suspected gaps. Record requirement-linked methods, outcomes and coverage limits using the common result outline. Keep the candidate unchanged during validation; changes require a fresh pass.
2. PASS requires successful required checks, sufficient coverage and zero actionable failures. Task passes alone are insufficient. Distinguish observed failures from missing capabilities or unresolved requirements. These remain blockers and never become invented product requirements or fictitious repair tasks. Report planning/acceptance defects with the affected task references for correction by its retained planner; required behavior changes need user authority.
3. For actionable implementation failures grounded in existing requirements, create exactly one repair specification for this failed validation pass, containing all such findings. Write `tasks/repair-NNN.md` in the selected bundle and append its relative path once to `task_order.md`. Choose the next unused repair number across existing repair filenames and order entries. Preserve existing specifications and order entries; do not edit implementation. Each finding records the source requirement, expected behavior, observed failure and reproduction evidence; include scope, required rechecks and any additional prerequisites. Order placement already gates the repair on preceding accepted tasks.
4. Make repair creation resumable: first record the validation pass/result and intended repair path in run evidence. On resume, inspect that identified pass's record, existing repair file and order entry before allocating. Reuse its reserved/existing path, complete a missing file or append only a missing entry, and preserve recorded findings. A collision belonging to another pass is a blocker to resolve, not authority to overwrite. Resume an outstanding recorded repair instead of creating a second task for the same failures. A later failed pass after repair acceptance can receive the next repair number.
5. Return status, validation result path, repair specification/order references, blockers and usage references. The supervisor schedules each new repair with a new planner and implementer through ordinary fresh reviews, then launches a fresh validator. Until validation passes, the assembled app remains incomplete. Validation never performs its own implementation repairs.
