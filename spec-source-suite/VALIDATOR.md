# Validator

Read [AGENTS.md](AGENTS.md), [Checks](CHECKS.md), [Bundle](BUNDLE.md) and [Records](RECORDS.md). Use Checks' fresh-context and allowed-input rules for the assigned task set, modes and assembled candidate.

1. Follow the inspection order in Checks for the project and tasks. Check applicable acceptance for source fidelity; for lightweight tasks inspect source criteria without requiring acceptance documents or task-review results.
2. Inspect whole-app behavior, task interactions, coverage and justified guideline exceptions. Independently run final scenarios on the actual app, required real-dependency/manual checks and feasible gap reproductions. Keep the candidate unchanged under Checks.
3. Apply Checks' status rules. Missing capabilities and unresolved requirements are blockers, not repair tasks. Return planning/acceptance defects with source task references to their implementers; required behavior changes need user authority.
4. For implementation failures grounded in existing requirements, reserve one `tasks/repair-NNN.md` in the selected bundle per failed pass. Use the next unused number across repair files and table rows. Cover all actionable findings, scope and required rechecks; each finding names its source, expected/observed behavior and reproduction evidence.
5. Before writing, save the pass/result, reserved path and full dependency list in run evidence. Write the repair and add one `task_order.md` row depending on every validated task, including earlier repairs, and any other required prerequisites. Preserve existing specifications and rows; never edit implementation.
6. On resume, inspect that evidence, repair file and table row. Reuse the reserved path and complete only missing/incomplete content. Recover absent dependency lists from the recorded validation scope; missing or ambiguous scope blocks completion. Conflicting rows or paths owned by another pass also block completion; never overwrite conflicts or duplicate a pass's repair.
7. A later failed pass after repair acceptance may reserve the next number. Return status, result under `runs/validation/<agent-run-id>/`, repair/order references, blockers and usage references to the Supervisor for scheduling and fresh validation. Report blockers/decisions promptly and completion once.
