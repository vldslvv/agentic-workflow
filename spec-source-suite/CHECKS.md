# Checks and acceptance

Read when preparing checks, inspecting a candidate or assessing results. Source authority follows [Bundle](BUNDLE.md); engineering constraints follow [Guidelines](GUIDELINES.md).

- Derive acceptance from original requirements before coding. Cover every applicable clause: normal, boundary, failure and interaction behavior. Keep private design choices in the plan unless a source requires them.
- An omitted requirement remains a defect even if listed checks pass. Correct acceptance against its sources, preserve approved history, and repeat affected checks and required independent review.
- Use proportionate observable checks, relevant regressions and required manual/real-dependency checks. Reuse meaningful tests; cover gaps through public interfaces. Reject tests of their own mock outputs, implementation details and test-only production hooks.
- `PASS` requires successful required checks, adequate requirement coverage and no unresolved actionable findings. Execution success and coverage are separate judgments.
- Observed violations are `FAIL`. Unavailable required capabilities or unresolved requirements are `BLOCKED`; skipped checks are `NOT_RUN` or `BLOCKED`. Record substitutes and coverage gaps without weakening expectations. Missing required fresh review is `INDEPENDENT_REVIEW_NOT_RUN` and blocks acceptance.
- For independent review/validation, start without inherited conversation. Establish expectations from original requirements and guidelines before acceptance or code. Allowed inputs are source requirements, applicable acceptance, candidate, factual check results, contracts, justified guideline exceptions and prior findings. Exclude plans, conversations, memory, author correctness claims, design narratives and copies embedded in other files.
- Keep the candidate unchanged during independent checks, including relevant dependencies, configuration and check inputs. Identify its location and revision when available; use existing version information without requiring commits or locks. Report changes and repeat affected independent checks in a fresh context.
- Independently execute relevant checks and feasible reproductions using declared setup, cleanup, pass rules and sampling/thresholds. Record evidence in the [result template](templates/result.md); manual judgments identify authority and artifact. Separate cleanup errors from primary failures.
- Batch independent reads and commands; print only needed output. Repeat successful checks only after relevant changes, failures, new concerns or a required independent check. Reassess affected results when sources, guidelines, dependencies or implementation change. Preserve unfinished work and blockers on cancellation or limits.
