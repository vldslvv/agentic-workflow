# Regeneration and cross-target reconstruction

Use with Generate when rebuilding without prior implementation. Cross-target reconstruction changes technology while preserving required behavior. Porting with access to prior code is a different claim.

1. Define scope, approved behavior, target, retained assets/data/services and required compatibility checks. Retained inputs are not reconstructed outputs. Preserve required outcomes, thresholds and fixtures; target-specific invocation may change without weakening them.
2. Use a new workspace and fresh worker contexts. Export only approved requirements, acceptance, public contracts/examples, permitted retained inputs and relevant suite guidance. Exclude prior implementation, build products, repository history, old plans, conversations, caches containing prior implementation and all project memory/copies. Prepare new plans from allowed inputs. Keep credentials out of exports and logs; reject traversal and symlink escapes. Preserve the original workspace and historical evidence.
3. Inspect exported inputs and report actual separation, including filesystem access, parent instructions, session memory, caches, remotes and network. Procedural separation is the default claim. If enforced isolation is required, apply and test access controls for the declared boundary, including excluded inputs and reviewer results; unavailable controls block that requirement. A fresh directory or instructions alone do not enforce isolation. Known prior-code leakage invalidates reconstruction claims; ordinary conformance evidence can still be reported separately.
4. Run Generate inside the new boundary. Run integration checks against required retained dependencies. Resume only work from this reconstruction and label it resumed. Report target changes, retained boundaries, actual controls/limits and observed conformance. Finite checks do not establish universal equivalence or reconstruction reliability.
